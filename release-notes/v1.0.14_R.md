# 1.0.14_R — 排队等待治理 + Kimi 工具协议 + 企业 VPC（网关 2026.11.11.1_upstream–2026.11.13.1_upstream）

自 v1.0.13_R 以来的全部改进：并入上游 v1.9.5–v1.9.8 共 18 提交，外加一处针对「上游全局排队导致调用不了」的等待治理。最直接的体感是**高峰期不再 3 分钟就放弃**。

## ⏳ 上游全局排队时的等待治理（2026.11.12.1_re，fork 自有）

- **现象**：上游把所有模型、所有账号、cn+intl 全部排起（`isQueued`、`queueType=p4`、`retryAfterSeconds=60`）时，网关每 ~184 秒就失败一次——**账号其实 6/6 全健康**，只是上游在排队。
- **改法**：
  - 排队等待改为**按总预算（600s）持续等**，而不是固定 3 轮（183 秒）就放弃——比上游 60 秒放行更早；
  - **排队期间释放账号信号量**（否则 4 个 CN 号的槽位被排队请求占满 → `all N busy` → 误报「无可用账号」）；
  - 排队耗尽统一转 **429 + Retry-After**（信封层排队信号记入 usage_ctx）；非流式 / responses 聚合路径补 `except RateLimited`（此前落到 `except Exception` 被包成 502，客户端看到的是 502 而不是可重试的 429）。
- **影响**：上游排队期间你的请求会**多等一会儿**而不是立刻失败；等到放行就直接成功，不再反复重试。

## 💭 Kimi 工具协议修复（#153）

- 展示名与内部 key 统一识别，Kimi 纳入 CN / INTL 的默认结构化工具历史；
- 有工具且本轮允许调用时，在系统提示后追加**稳定的原生工具通道与 JSON 转义/schema 约束**（不覆盖客户端提示、不改工具 schema、推理强度与采样参数）；
- 保留坏参数协议校验：**不猜测补齐后执行、不自动重发收费请求**；显式关闭结构化历史仍有效；
- 新增 109 项 Kimi 行为回归（十步历史、三协议桥接、前缀稳定、输入/schema 不变、非法参数校验）。

## 🔒 Windows 升级后的静默双开（PR #155）

- Windows 的 `SO_REUSEADDR` 允许第二个 socket 绑一个**正在监听**的端口：升级时新进程先起、旧进程后退，守卫把应答者判成 stale 后继续 bind —— **这个 bind 不会失败**，两个实例同时 listen，连接静默分流到旧实例，`/health` 永远回旧版本、看板永远提示「有新版本」。
- 改用 `SO_EXCLUSIVEADDRUSE` 独占绑定（抢绑直接 WSAEADDRINUSE），POSIX 保留地址复用；维护者移除了原 PR 的「降级兼容 socket」回退（那等于重新打开双开大门）。

## 🏢 企业 VPC 专属域（PR #150）

- `QD_CN_VPC_ENDPOINT`：从实例名或专属域统一推导 CN 的登录官网、OpenAPI 与推理网关三主机；**未配置时行为完全不变**，INTL 网关不变；
- 审查补强：VPC 模式隔离凭证探测（不用公网/其它实例的历史额度缓存）、重定向限制在本实例的三个 HTTPS 端口、**fake-IP DNS 同时返回 IPv4 / IPv4-mapped / IPv4-translated IPv6 时，混入真实私网地址仍拒绝**、实例名最长 55 字符校验。

## 🧾 其它
